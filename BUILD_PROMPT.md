# Build Spec: Telegram Job Catcher

Build a Node.js tool that reads job postings from Telegram channels I follow,
filters them against my profile, and forwards the relevant ones to my own
private Telegram channel in a clean, structured format.

Build the whole thing end to end, test it yourself as far as you can, and fix
what breaks. Do not stop between sections to ask permission to continue.

**Two things you must NOT do yourself, because they need my credentials:**

1. Do not run the interactive login script. Write it, then tell me to run it and
   paste the resulting session string into `.env` myself.
2. Do not run anything that actually posts to my Telegram channel until the dry
   run below passes and I confirm.

Everything else — writing, installing, running the connection checks, fixing
errors — is yours to do without asking.

If something is genuinely ambiguous, make a reasonable choice, note it in the
README under "Decisions I made", and keep going. Ask me only if you are blocked
by something you cannot decide or test.

## Architecture

**Reading** uses my personal Telegram account via MTProto (the `telegram` /
GramJS package). A bot cannot read channels it is not an admin of, so the user
account is required.

**Sending** uses a separate Telegram bot (from @BotFather) that is an admin of
my private channel. My personal account must never post anything.

**State** lives in MongoDB Atlas free tier (M0).

**Scheduling** is a GitHub Actions workflow on a cron. The script wakes, polls,
sends, and exits. It is not a daemon.

### Seniority filtering

Some seniority levels are far enough from my experience to be pure noise and
should be rejected outright; others are worth flagging but still sending.

**Hard reject — title only, never the full message body:**

```
staff engineer, staff software, principal, architect, head of,
director, vp of engineering, engineering manager, cto,
7+ years, 8+ years, 10+ years, lead, tech lead
```

Job descriptions routinely contain phrases like "you will report to a
Principal Engineer" inside listings that are themselves junior roles —
matching the whole body would silently discard good jobs, so this check runs
against the job title (the first line) only.

(`lead` and `tech lead` moved here from the soft list after the initial
build — originally they were meant to stay soft since "Tech Lead" at a small
company can mean a team of three, but that turned out to be too permissive
in practice. `senior` stays soft.)

**Soft signals (flag, do not reject):**

```
senior, 3+ years, 4+ years, 5+ years
```

Annotate the message with a warning emoji (⚠️) but still send it. `senior`
stays soft on purpose: many listings say "senior" while actually accepting
mid-level.

When a message is rejected for seniority, log one clear line:
`[SKIP:LEVEL] "<title>" — matched "<the keyword that triggered it>"` — so it's
possible to scan the log and confirm nothing good is being thrown away.

## Build order

### 1. Session and channel discovery

1. `src/login.js` — one-time interactive login using `StringSession`, prints a
   session string to paste into `.env`. Warn the user that this string grants
   full account access.
2. `src/list-channels.js` — reads my Telegram folders via
   `Api.messages.GetDialogFilters()`, finds the folder named "Jobs" (accept a
   different name as a CLI argument), resolves the peers in it to channel names,
   and saves them to `data/channels.json`.

Handle both possible shapes of the filters response (bare array vs object with
a `.filters` property), and both shapes of a filter title (plain string vs an
object with a `.text` property) — these vary by protocol layer.

### 2. Reading messages

Read new messages per channel, tracking the last seen `message_id` per channel
in MongoDB so nothing is re-read. On the very first run, only look back 24
hours — do not pull full channel history.

For each message extract:

- **Link.** Check these sources in order, take the first hit:
  1. `replyMarkup` inline keyboard buttons (many channels put "Apply" in a
     button — this is NOT in entities and is easy to miss)
  2. `MessageEntityTextUrl` — its `.url` property (hidden link behind text)
  3. `MessageEntityUrl` — a bare URL in the text
  4. `MessageEntityEmail` — fall back to an application email

- **Date.** `message.date` is a Unix epoch in UTC. If the message is a forward,
  use `message.fwdFrom.date` instead — otherwise a year-old job reposted today
  looks fresh. Convert to Africa/Cairo for display.

- **Telegram permalink** to the original message, so I can open the source post.

- **Title / company / location.** Best-effort parsing: title is the first line
  containing real text after stripping emoji and blank lines. Company and
  location come from lines starting with recognizable markers (🏢, 📍,
  `Company:`, `Location:`, and the Arabic equivalents `شركة`, `المكان`).
  If parsing fails, still send the job with whatever was extracted — never drop
  a message because parsing was imperfect.

### 3. Filtering

Score each message against the keyword lists above. Normalize Arabic text
(strip diacritics, unify hamza and alef forms) and lowercase Latin text before
matching. Use word boundaries so "Java" does not match "JavaScript" and "node"
does not match unrelated substrings.

**Deduplication:** the same job is posted across many channels. Hash the
normalized message text and skip anything already sent. Store sent hashes in
MongoDB with a TTL index so the collection does not grow forever.

**Age cutoff:** skip anything older than 7 days.

### 3.5 AI analysis layer

Runs **after** the keyword filter (and after dedup and the age cutoff),
**never before it** — the keyword filter throws away the ~90% of channel
traffic that is ads, courses, and irrelevant stacks, and the AI only ever
sees what survived that. This keeps the free-tier quota comfortable and the
run fast.

Pipeline: `raw messages → dedup → keyword filter → age cutoff → AI analysis
→ format and send`.

Model: Google Gemini Flash, free tier, via `GEMINI_API_KEY`. Do not hardcode
rate-limit numbers — read the limit from the API's error response and back
off accordingly. A small concurrency limit (2–3 parallel calls) keeps a large
batch from tripping the per-minute cap.

The AI now owns title/company/location/summary extraction (the regex/emoji
parser stays in the code as the fallback path, never deleted). Ask the model
for JSON only (no prose, no markdown fences):

```json
{
  "is_job": true,
  "matches_me": true,
  "confidence": 0.85,
  "title": "Full Stack Developer",
  "company": "Solo Clash",
  "location": "Dubai, UAE",
  "work_mode": "onsite",
  "seniority": "mid",
  "stack": ["React", "Node.js", "MongoDB"],
  "summary": "سطرين بالعربي عن الوظيفة",
  "reason": "why this does or does not fit me",
  "apply_link": "https://...",
  "apply_email": null
}
```

The system prompt includes my profile (see the "My profile" section above)
and these judgement rules: anything JS/TS-based is a match (including React
Native, Expo, Ionic, Electron — mobile/desktop doesn't disqualify it); the
full stack doesn't need to be present (React-only, Node-only, or generic
"Software Engineer" all count); blockchain/Web3/Solidity is a strong match;
be lenient about seniority, only reject on level if the role clearly needs
many more years of experience than I have; reject non-engineering roles,
courses, training ads, paid-internship ads, recruiter spam with no real job,
and roles whose core language isn't JS/TS; if it's not a job at all, set
`is_job` to false and stop.

**Robustness is the point of this layer, not a nice-to-have:**

- Strip markdown code fences before parsing (the model wraps JSON in them
  regularly despite instructions not to).
- Validate the parsed object against the expected shape — missing or
  wrong-typed fields must not crash the run.
- On any AI failure (bad JSON, timeout, quota exhausted, network error), fall
  back to the existing keyword result and the regex parser, and send the job
  anyway. A broken AI layer degrades to the previous behaviour, never to
  silence.
- Log every fallback with the reason, and include an AI-failure count in the
  run summary.
- Cache AI results in MongoDB keyed by the message text hash, so a repost
  across channels is never analysed twice.
- The whole layer sits behind an `AI_ENABLED` environment flag, default on.

`npm run dry` prints, for every message, both verdicts side by side —
`KEYWORD: match (score 7)  |  AI: match (0.85) — "Strong React/Node fit,
mid-level"` — plus counts in the run summary of where the two agreed, where
the AI rescued something keywords would have dropped, and where the AI
rejected something keywords accepted. In this comparison mode the AI runs
regardless of the keyword verdict (purely for tuning); in the live run it
only ever runs on messages that already passed the keyword filter, to
conserve quota.

### 4. Sending

Send to my private channel through the bot, one message per job:

```
**{title}**
🏢 {company}
📍 {location}
🕐 {relative age, e.g. "منذ ساعتين"} · {absolute date}
📡 {source channel name}

{summary, max 300 chars}

🤖 {AI's reasoning, only when the AI layer actually ran}

🔗 Apply: {link}
💬 [البوست الأصلي]({telegram permalink})
```

Omit any line whose value is missing rather than printing an empty label.
Respect the Telegram Bot API rate limit (roughly 20 messages/minute to a
channel) — throttle sends.

### 5. Deployment

GitHub Actions workflow running every 30 minutes. Secrets: `TG_API_ID`,
`TG_API_HASH`, `TG_SESSION`, `BOT_TOKEN`, `CHANNEL_ID`, `MONGODB_URI`,
`GEMINI_API_KEY`.

Note in the README that GitHub disables scheduled workflows on public repos
after 60 days of inactivity, and that cron timing can drift by 5–20 minutes.

### 5.5 Dashboard, job persistence, and monthly cleanup

A read-only Next.js dashboard (`/dashboard`, a fully separate project —
see DASHBOARD_PROMPT.md) reads collected jobs and is deployed to Vercel,
while the collector keeps running on GitHub Actions. Two collector-side
changes support it:

- The collector now persists the full structured job record (not just a
  sent-hash) to a `jobs` collection every time it actually sends a message
  — see `src/lib/db.js`'s `insertJobRecord` and `src/lib/run.js`. This is
  what the dashboard renders.
- Since `jobs` has no TTL index (the dashboard needs to keep showing weeks
  of history), a monthly cleanup (`src/lib/cleanup.js`) deletes job
  documents older than `RETENTION_DAYS` (default 60), gated to run at most
  once every `CLEANUP_INTERVAL_DAYS` (default 30) via a `meta.last_cleanup_at`
  timestamp checked at the start of every live run. `sent_hashes`,
  `channel_state`, and the rest of `meta` are never touched by it.
  `npm run cleanup -- --dry` reports what it would delete without deleting
  anything.

See DASHBOARD_PROMPT.md for the full spec this was built from, and the
README's "Dashboard" and "Deploying the dashboard to Vercel" sections for
how to run and deploy it.

## Required helper scripts

These exist so I have to do as little manual work as possible.

- **`npm run doctor`** — checks every environment variable is present, connects
  to Telegram, connects to MongoDB, and verifies the bot can see my channel.
  Prints a clear pass/fail line for each. This is the first thing I run.

- **`npm run channel-id`** — resolves my private channel's numeric id
  automatically (via the bot's `getUpdates`, or by listing the bot's chats) and
  prints the line to paste into `.env`. I should not have to look this up by
  hand. Note in the output that a private channel id starts with `-100`.

- **`npm run dry`** — a full end-to-end run with sending disabled. Reads real
  messages, filters them, runs the AI layer (printing a keyword-vs-AI
  comparison line for every message, see section 3.5), and prints the exact
  messages it *would* send to the console, plus the run summary. Nothing is
  written to the database and nothing is posted. **This is how we test before
  going live.**

- **`npm start`** — the real run.

## Error handling requirements

- Catch `FloodWaitError` from Telegram, log the required wait, and skip that
  channel for this run rather than crashing the whole job.
- One failing channel must never abort the remaining channels.
- If MongoDB is unreachable, fail loudly with a clear message — do not silently
  send duplicates.
- Log a per-run summary: channels scanned, messages read, matched, sent,
  skipped as duplicates, rejected for seniority, and — for the AI layer — how
  many calls fell back, and how many messages the AI agreed with / rescued /
  overrode versus the keyword filter.
- On any AI failure, fall back to the keyword result and the regex parser and
  send the job anyway — never drop a job because the AI layer broke.
